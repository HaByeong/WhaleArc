1.4 JWT 인증 흐름 상세

시퀀스 다이어그램

1. [로그인] Client → POST /auth/login {userId, password} Server → BCrypt 비밀번호 검증 → Access Token 생성 (HS256, 1시간) → Refresh Token 생성 (HS256, 7일) → DB에 저장 → Response Body: {userId, accessToken} → Set-Cookie: refreshToken (HttpOnly, Secure, SameSite=Strict) 2. [API 요청] Client → Authorization: Bearer {accessToken} Server → JwtAuthenticationFilter.doFilterInternal() → validateToken() : 서명 + 만료 검증 → (유효) getUserIdFromToken() → SecurityContext에 인증정보 설정 → (무효) SecurityContext 비어있음 → Spring Security가 401 반환 3. [토큰 만료 시 자동 갱신] Client → API 요청 → 401 응답 Client → Axios Response Interceptor 동작 → POST /auth/reissue (Cookie에 refreshToken 자동 전송) Server → 쿠키에서 refreshToken 추출 → 서명/만료 검증 → DB 저장된 refreshToken과 비교 (Replay Attack 방지) → 새 accessToken 발급 Client → localStorage에 새 토큰 저장 → 원래 요청 재시도 4. [로그아웃] Client → POST /auth/logout Server → SecurityContext에서 userId 추출 (Request Body가 아님 → 스푸핑 방지) → DB의 refreshToken = null (서버사이드 무효화)

JwtTokenProvider.java — 토큰 생성/검증
@RequiredArgsConstructor
public class JwtTokenProvider {
    private final SecretKey secretKey;  // SecurityConfig에서 Bean 주입

    // Access Token 생성 (1시간)
    public String generateAccessToken(String userId) {
        return Jwts.builder()
                .setSubject(userId)           // payload에 userId 저장
                .claim("role", "user")        // 역할 정보
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + ACCESS_TOKEN_TIME))
                .signWith(secretKey, SignatureAlgorithm.HS256)  // HMAC-SHA256 서명
                .compact();
    }

    // Refresh Token 생성 (7일)
    public String generateRefreshToken(String userId) {
        return Jwts.builder()
                .setSubject(userId)
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + REFRESH_TOKEN_TIME))
                .signWith(secretKey, SignatureAlgorithm.HS256)
                .compact();
    }

    // 토큰 유효성 검증
    public boolean validateToken(String token) {
        try {
            Jwts.parserBuilder().setSigningKey(secretKey).build().parseClaimsJws(token);
            return true;
        } catch (SecurityException | MalformedJwtException e) {
            // 서명 불일치 또는 형식 오류
        } catch (ExpiredJwtException e) {
            // 만료된 토큰
        } catch (UnsupportedJwtException | IllegalArgumentException e) {
            // 지원하지 않는 토큰 또는 잘못된 인자
        }
        return false;
    }
}

핵심 코드: JwtAuthenticationFilter.java

JwtAuthenticationFilter.java — 요청마다 토큰 검증
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider jwtTokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
            HttpServletResponse response, FilterChain filterChain) {
        String header = request.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.replace("Bearer ", "");

            // [보안 개선] 토큰 검증을 먼저 수행
            // 기존: 바로 getUserIdFromToken() → 만료 토큰 시 500 에러 + 스택트레이스 노출
            // 수정: validateToken()이 false → SecurityContext 비어있음 → 401 자동 반환
            if (jwtTokenProvider.validateToken(token)) {
                String userId = jwtTokenProvider.getUserIdFromToken(token);
                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(userId, null, List.of());
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        filterChain.doFilter(request, response);
    }
}

핵심 코드: UserLoginService.java — 로그인 + 쿠키 생성

UserLoginService.java
@Service
@RequiredArgsConstructor
public class UserLoginService implements UserLoginServiceInterface {
    private final UserRepository userRepository;
    private final BCryptPasswordEncoder bcryptPasswordEncoder;
    private final JwtTokenProvider jwtTokenProvider;

    @Override
    public ResponseEntity login(UserLoginRequestDto dto) {
        String requestId = dto.getUserId();
        // DB에서 암호화된 비밀번호만 조회 (전용 DTO 사용)
        RepositoryPasswordReturnDto pwDto = userRepository.findOnlyPasswordById(requestId);

        if (pwDto.getPassword() == null ||
            !bcryptPasswordEncoder.matches(dto.getPassword(), pwDto.getPassword())) {
            throw new IllegalArgumentException("아이디 혹은 비밀번호가 일치하지 않습니다");
        }

        // Refresh Token 생성 → DB에 저장 (로그아웃/재발급 시 비교용)
        String refreshToken = jwtTokenProvider.generateRefreshToken(requestId);
        User user = userRepository.findByUserId(requestId);
        user.setJwtRefreshToken(refreshToken);
        userRepository.save(user);

        // HttpOnly 쿠키에 Refresh Token 담기
        ResponseCookie cookie = ResponseCookie.from("refreshToken", refreshToken)
                .httpOnly(true)       // JavaScript 접근 차단 (XSS 방어)
                .secure(true)         // HTTPS에서만 전송
                .path("/")            // 모든 경로에서 쿠키 전송
                .maxAge(7*24*60*60)   // 7일
                .sameSite("Strict")   // 같은 사이트에서만 전송 (CSRF 방어)
                .build();

        return ResponseEntity.ok()
                .header(HttpHeaders.SET_COOKIE, cookie.toString())
                .body(new UserLoginResponseDto(requestId,
                    jwtTokenProvider.generateAccessToken(requestId)));
    }
}

ExchangeAccountService.java (핵심 부분)
@Service
@RequiredArgsConstructor
public class ExchangeAccountService {
    private final ExchangeAccountRepository repository;
    private final AESCryptoUtil aesCryptoUtil;
    private final KisApiClient kisApiClient;
    private final UpbitApiClient upbitApiClient;
    private final BitgetApiClient bitgetApiClient;

    // API 키 저장 (AES-GCM 암호화)
    public ExchangeAccount saveAccount(String userId, ExchangeAccountRequestDto request) {
        Optional<ExchangeAccount> existing = repository
                .findByUserIdAndExchangeType(userId, request.getExchangeType());

        ExchangeAccount account = existing.orElseGet(() -> {
            ExchangeAccount a = new ExchangeAccount();
            a.setUserId(userId);
            a.setExchangeType(request.getExchangeType());
            a.setCreatedAt(LocalDateTime.now().toString());
            return a;
        });

        // 핵심: 평문 API 키를 AES-GCM으로 암호화 후 저장
        account.setApiKey(aesCryptoUtil.encrypt(request.getApiKey()));
        account.setSecretKey(aesCryptoUtil.encrypt(request.getSecretKey()));
        // KIS 전용 필드
        if (request.getAppSecret() != null)
            account.setAppSecret(aesCryptoUtil.encrypt(request.getAppSecret()));
        if (request.getAccountNumber() != null)
            account.setAccountNumber(request.getAccountNumber()); // 계좌번호는 비암호화 (URL 구성용)

        account.setConnected(true);
        account.setUpdatedAt(LocalDateTime.now().toString());
        return repository.save(account);
    }

    // 포트폴리오 조회 (복호화 → 거래소 API 호출)
    public ExchangePortfolioDto getPortfolio(String userId, String exchangeType) {
        ExchangeAccount account = repository
                .findByUserIdAndExchangeType(userId, exchangeType)
                .orElse(null);
        if (account == null || !account.isConnected()) return emptyPortfolio(exchangeType);

        // 복호화된 키로 실제 API 호출
        String apiKey = aesCryptoUtil.decrypt(account.getApiKey());
        String secretKey = aesCryptoUtil.decrypt(account.getSecretKey());

        switch (exchangeType) {
            case "KIS":
                String appSecret = aesCryptoUtil.decrypt(account.getAppSecret());
                return kisApiClient.getPortfolio(apiKey, secretKey, appSecret,
                        account.getAccountNumber());
            case "UPBIT":
                return upbitApiClient.getPortfolio(apiKey, secretKey);
            case "BITGET":
                return bitgetApiClient.getPortfolio(apiKey, secretKey);
            default:
                return emptyPortfolio(exchangeType);
        }
    }
}

1.6 API 키 암호화 (AES-GCM) 상세

AESCryptoUtil.java — AES-256-GCM 암호화/복호화
@Component
public class AESCryptoUtil {
    private static final String ALGORITHM = "AES/GCM/NoPadding";
    private static final int GCM_TAG_LENGTH = 128;  // 인증 태그 128bit
    private static final int IV_LENGTH = 12;         // GCM 권장 IV 12bytes

    private final SecretKeySpec keySpec;

    public AESCryptoUtil(@Value("${exchange.encryption-key}") String key) {
        byte[] keyBytes = Arrays.copyOf(key.getBytes(StandardCharsets.UTF_8), 16);
        this.keySpec = new SecretKeySpec(keyBytes, "AES");
    }

    public String encrypt(String plainText) {
        byte[] iv = new byte[IV_LENGTH];
        new SecureRandom().nextBytes(iv);  // 매번 랜덤 IV 생성 → 같은 평문도 다른 암호문

        Cipher cipher = Cipher.getInstance(ALGORITHM);
        cipher.init(Cipher.ENCRYPT_MODE, keySpec, new GCMParameterSpec(GCM_TAG_LENGTH, iv));
        byte[] encrypted = cipher.doFinal(plainText.getBytes(UTF_8));

        // IV(12bytes) + 암호문을 결합 → Base64 인코딩
        byte[] combined = new byte[IV_LENGTH + encrypted.length];
        System.arraycopy(iv, 0, combined, 0, IV_LENGTH);
        System.arraycopy(encrypted, 0, combined, IV_LENGTH, encrypted.length);
        return Base64.getEncoder().encodeToString(combined);
    }

    public String decrypt(String encryptedText) {
        byte[] combined = Base64.getDecoder().decode(encryptedText);
        byte[] iv = Arrays.copyOfRange(combined, 0, IV_LENGTH);          // 앞 12바이트 = IV
        byte[] encrypted = Arrays.copyOfRange(combined, IV_LENGTH, combined.length); // 나머지 = 암호문

        Cipher cipher = Cipher.getInstance(ALGORITHM);
        cipher.init(Cipher.DECRYPT_MODE, keySpec, new GCMParameterSpec(GCM_TAG_LENGTH, iv));
        return new String(cipher.doFinal(encrypted), UTF_8);
    }
}
GCM vs CBC: GCM은 암호화와 동시에 인증 태그를 생성해 데이터 위변조를 감지합니다. CBC는 별도의 HMAC이 필요합니다. 금융 데이터처럼 무결성이 중요한 경우 GCM이 적합합니다.

const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080',
  headers: { 'Content-Type': 'application/json' },
  withCredentials: true,  // 쿠키 자동 전송 (RefreshToken)
});

// Request Interceptor: 모든 요청에 JWT 토큰 자동 첨부
apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem('accessToken');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Response Interceptor: 401 → 자동 토큰 갱신 → 원래 요청 재시도
apiClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      try {
        // RefreshToken은 쿠키에서 자동 전송 (withCredentials: true)
        const res = await axios.post(`${API_BASE_URL}/auth/reissue`, {},
            { withCredentials: true });
        const { accessToken } = res.data;
        localStorage.setItem('accessToken', accessToken);
        error.config.headers.Authorization = `Bearer ${accessToken}`;
        return apiClient.request(error.config);  // 원래 요청 재시도
      } catch {
        localStorage.removeItem('accessToken');
        localStorage.removeItem('userId');
        window.location.href = '/login';  // 재발급도 실패 → 로그인 페이지
      }
    }
    return Promise.reject(error);
  }
);
이 패턴의 장점: 사용자는 토큰 만료를 인식하지 못한 채 자연스럽게 서비스를 이용합니다. Access Token이 만료되면 백그라운드에서 자동으로 갱신하고 원래 요청을 재시도합니다.

2. 면접 예상 질문 + 모범 답변

2.A WhaleArc 프로젝트 심층 질문

Q1. "프로젝트 전체 아키텍처를 설명해주세요"
WhaleArc는 React+TypeScript 프론트엔드와 Spring Boot 백엔드, MongoDB로 구성된 모의투자 플랫폼입니다.

프론트엔드는 Vite로 빌드하고, 10개 페이지를 React Router로 라우팅합니다. Axios Interceptor를 통해 JWT 토큰 자동 첨부와 만료 시 자동 갱신을 처리합니다.

백엔드는 크게 인증 모듈과 거래소 연동 모듈로 나뉩니다. 인증은 JWT 기반으로 Access Token(1시간)과 Refresh Token(7일)을 분리 운영하고, 거래소 연동은 Strategy 패턴을 적용해 KIS/업비트/비트겟 3개 거래소를 독립적으로 처리합니다. API 키는 AES-GCM으로 암호화해서 MongoDB에 저장합니다.

설계 원칙으로는 계층 분리(Controller→Service→Repository), 인터페이스 기반 서비스, 생성자 주입(DI)을 적용했습니다.
"왜 세션이 아니라 JWT를 선택했나요?" → Stateless 특성 덕분에 서버 확장 시 세션 공유 문제가 없고, 프론트엔드가 별도 도메인(:5173)에서 돌아가므로 쿠키 기반 세션보다 JWT가 적합했습니다.
Q2. "JWT 인증 보안을 어떻게 강화했나요?"
6가지 보안 포인트를 적용했습니다:
1) 토큰 분리: Access Token(짧은 수명)은 Body로, Refresh Token(긴 수명)은 HttpOnly 쿠키로 전달
2) XSS 방어: HttpOnly 플래그로 JavaScript에서 Refresh Token 접근 차단
3) CSRF 방어: SameSite=Strict로 크로스사이트 요청 시 쿠키 미전송
4) Replay Attack 방지: Refresh Token을 DB에 저장하고, 재발급 시 DB 값과 비교
5) 서버사이드 로그아웃: 로그아웃 시 DB의 Refresh Token을 null로 설정
6) ID 스푸핑 방지: userId를 Request Body가 아닌 SecurityContext에서 추출
"Access Token이 탈취되면 어떻게 되나요?" → 1시간 후 자동 만료됩니다. 더 강화하려면 토큰 블랙리스트(Redis)를 도입하거나, Refresh Token Rotation을 적용할 수 있습니다.
Q3. "AES-GCM 암호화를 선택한 이유와 동작 원리를 설명해주세요"
API 키는 외부 거래소와 통신할 때 평문으로 필요하므로 단방향 해싱(BCrypt)이 아닌 양방향 암호화가 필요합니다.

GCM 모드를 선택한 이유:
- CBC+HMAC 조합 대비 하나의 연산으로 기밀성(암호화) + 무결성(인증 태그)을 동시 보장
- 128bit 인증 태그로 암호문이 변조되면 복호화 시 자동 감지 → 금융 데이터 무결성에 적합

동작 원리:
1) 12바이트 랜덤 IV를 SecureRandom으로 생성 (매번 다른 IV → 같은 키도 다른 암호문)
2) AES-GCM으로 평문 암호화 + 128bit 인증 태그 생성
3) IV(12B) + 암호문을 결합해 Base64 인코딩 후 MongoDB에 저장
4) 복호화 시 앞 12바이트를 IV로 분리, 나머지를 암호문으로 복호화
"IV를 왜 암호문과 같이 저장하나요?" → IV는 비밀이 아닙니다. 복호화에 필요한 파라미터일 뿐이고, 공개되어도 보안에 영향 없습니다. 중요한 건 같은 IV를 재사용하지 않는 것입니다.
Q4. "3개 거래소 연동에 Strategy 패턴을 적용했다고 했는데, 구체적으로 설명해주세요"
문제 상황: KIS는 OAuth2, Upbit은 JWT, Bitget은 HMAC 서명으로 인증 방식이 모두 다릅니다. 하나의 메서드에 if-else로 처리하면 코드가 복잡해지고, 새 거래소 추가 시 기존 코드를 수정해야 합니다.

해결: ExchangeAccountService가 exchangeType을 기준으로 해당 클라이언트에 위임합니다. 각 클라이언트(KisApiClient, UpbitApiClient, BitgetApiClient)는 독립적으로 인증 로직과 API 호출을 구현합니다.

장점:
- 새 거래소 추가 시 Client만 추가 → 기존 코드 수정 없음 (OCP)
- 각 클라이언트가 독립적 → 업비트 API 변경이 KIS에 영향 없음
- 클라이언트별 독립 테스트 가능
"현재 switch 문으로 분기하는데, 더 개선할 수 있는 방법은?" → Map<String, ExchangeApiClient> 같은 Registry 패턴을 적용하면 switch 없이 exchangeType으로 클라이언트를 자동 매핑할 수 있습니다. 인터페이스를 정의하고 @Qualifier나 Map 주입을 활용하면 됩니다.
Q5. "동시 주문 시 잔고 정합성 문제를 어떻게 해결했나요?"
문제: 동시에 여러 주문이 들어오면 잔고 검증이 병렬로 실행되어, 잔고 7000만원인데 7000만원짜리 주문 2건이 모두 통과하는 상황이 발생했습니다.

원인: 두 스레드가 동시에 잔고를 읽으면 둘 다 "7000만원 충분"으로 판단합니다.

해결: 사용자별 Lock을 적용했습니다. 같은 사용자의 주문은 순차적으로 처리되되, 다른 사용자의 주문에는 영향을 주지 않습니다.
- 잔고 조회 → 검증 → 차감 → 주문 생성을 하나의 임계 영역으로 묶음
- 잔고 검증 후에만 다음 주문이 처리되므로 정합성 보장

의미: 실제 증권사 OMS에서도 주문 체결 시 잔고/증거금 정합성이 핵심입니다. 규모는 다르지만, 동시성 제어의 본질적인 문제를 직접 경험하고 해결한 것이 의미 있었습니다.
"synchronized와 ReentrantLock 중 뭘 썼나요?" → 사용자별로 Lock을 분리해야 하므로 ConcurrentHashMap<String, ReentrantLock>을 사용했습니다. synchronized는 객체/메서드 단위라 사용자별 분리가 어렵습니다. "DB Lock은 고려 안 했나요?" → 규모가 커지면 SELECT ... FOR UPDATE 같은 비관적 Lock이나 낙관적 Lock(버전 필드)을 적용할 수 있습니다.
Q6. "왜 MongoDB를 선택했나요?"
선택 이유:
1) 스키마 유연성: 거래소별 필요한 필드가 다릅니다. KIS는 appSecret/accountNumber가 필요하지만 Upbit/Bitget은 불필요합니다. MongoDB는 이런 차이를 자연스럽게 수용합니다.
2) 도큐먼트 단위 독립성: 사용자별 포트폴리오, 거래소 계정이 독립적인 단위로 존재하므로 도큐먼트 모델에 적합합니다.
3) 빠른 프로토타이핑: 스키마 마이그레이션 없이 필드를 추가/변경할 수 있어 개발 속도가 빠릅니다.

한계 인식: 실제 증권 시스템에서는 트랜잭션 정합성이 핵심이므로 RDB(Oracle, PostgreSQL)가 더 적합합니다. MongoDB 4.0부터 Multi-Document Transaction을 지원하지만, 금융 시스템의 복잡한 조인과 ACID 요구사항에는 RDB가 유리합니다.
Q7. "백테스팅 엔진에서 일목균형표 오류를 어떻게 발견했나요?"
후행스팬(Lagging Span)은 현재 종가를 26일 전에 표시하는 지표입니다. 구현 시 수식 방향이 반대로 설정되어 26일 후에 표시되고 있었습니다. 이는 코드상 에러가 아니라(양수/음수 부호 차이) 금융 지식이 없으면 발견하기 어려운 논리적 오류였습니다.

발견 과정: 차트에 표시된 후행스팬이 미래 시점에 그려지는 것을 보고 "이건 선행스팬처럼 동작하고 있다"고 판단, 수식의 오프셋 부호를 수정했습니다.

추가 개선: 단순 수익률만 보여주던 백테스팅 결과에 MDD(최대 낙폭)와 샤프 비율을 추가하여 리스크 관리가 가능한 시스템으로 고도화했습니다.
"MDD와 샤프비율을 어떻게 계산했나요?" → MDD = (전고점 - 최저점) / 전고점. 일별 포트폴리오 가치의 고점 대비 최대 하락폭입니다. 샤프비율 = (포트폴리오 수익률 - 무위험수익률) / 수익률의 표준편차. 같은 수익률이라도 변동성이 낮을수록 샤프비율이 높아 우수한 전략입니다.
Q8. "프론트엔드에서 토큰 자동 갱신은 어떻게 구현했나요?"
Axios의 Response Interceptor를 활용했습니다.

1) API 요청이 401을 반환하면 Interceptor가 감지
2) /auth/reissue를 호출 (withCredentials:true → HttpOnly 쿠키의 RefreshToken 자동 전송)
3) 새 AccessToken을 받아 localStorage에 저장
4) 실패했던 원래 요청을 새 토큰으로 자동 재시도
5) 재발급도 실패하면 → 토큰 삭제 + 로그인 페이지 리다이렉트

사용자는 토큰 만료를 인식하지 못한 채 자연스럽게 서비스를 이용할 수 있습니다.
"동시에 여러 요청이 401을 받으면?" → 현재는 각각 reissue를 호출합니다. 개선 방법으로는 첫 번째 401에서만 reissue를 호출하고 나머지 요청은 Promise Queue에 대기시켜, 토큰 갱신 후 일괄 재시도하는 방식이 있습니다.

Q12. "트랜잭션의 ACID를 설명하고, OMS에서 왜 중요한지 말해주세요"
Atomicity(원자성): 전부 성공하거나 전부 실패. OMS에서 "잔고 차감 + 주문 생성"이 하나의 단위. 잔고는 차감했는데 주문이 실패하면 돈만 사라집니다.

Consistency(일관성): 트랜잭션 전후 데이터 무결성 유지. 잔고가 마이너스가 되면 안 되고, 매수 수량과 보유 수량이 일치해야 합니다.

Isolation(격리성): 동시 실행 트랜잭션이 서로 간섭 없음. 펀드A와 펀드B가 동시에 주문해도 각자의 잔고 검증이 독립적으로 이루어져야 합니다. WhaleArc에서 사용자별 Lock으로 이를 보장했습니다.

Durability(지속성): 커밋된 트랜잭션은 영구 보존. 체결된 주문 정보가 서버 장애로 사라지면 안 됩니다.

OMS에서의 중요성: 주문 1건의 오류가 수십억원의 손실로 이어질 수 있습니다. ACID는 금융 시스템의 신뢰성의 기반입니다.
Q13. "인덱스의 동작 원리와 장단점을 설명해주세요"
동작 원리: B-Tree(또는 B+Tree) 구조로 데이터를 정렬된 형태로 유지합니다. 루트 노드에서 리프 노드까지 탐색하면 O(log n)에 원하는 데이터를 찾을 수 있습니다.

예시: MongoDB에서 userId로 exchange_accounts를 조회할 때:
- 인덱스 없음: 모든 문서를 순차 스캔 (Collection Scan) → O(n)
- userId 인덱스: B-Tree 탐색 → O(log n)
- 100만 건 기준: 1,000,000번 vs ~20번 비교

장점: 조회 성능 대폭 향상
단점: 1) 쓰기 시 인덱스도 업데이트 → 쓰기 성능 저하 2) 추가 저장 공간 필요 3) 너무 많은 인덱스는 오히려 성능 저하

증권 시스템 적용: 주문번호, 종목코드, 사용자ID 등 조회가 빈번한 필드에 인덱스를 설정합니다.

Q15. "HashMap과 TreeMap의 차이를 설명하고, 각각 언제 사용하나요?"
HashMap: 해시 테이블 기반. 순서 없음. 평균 O(1) 조회/삽입. 해시 충돌 시 최악 O(n).
TreeMap: Red-Black Tree 기반. 키 기준 정렬. O(log n) 조회/삽입.

증권 시스템 활용:
- HashMap: 종목코드 → 시세 매핑 (빠른 조회가 핵심)
- TreeMap: 호가창 구현 (매수 호가는 높은 가격순, 매도 호가는 낮은 가격순 정렬 필요)

WhaleArc의 UpbitApiClient에서 Map<String, Double> prices에 HashMap을 사용한 이유는 코인별 현재가를 빠르게 조회하기 위해서입니다. 정렬이 필요 없는 단순 매핑이므로 O(1)인 HashMap이 적합합니다.
Q16. "JVM 메모리 구조를 설명해주세요"
Heap: 객체 인스턴스가 저장되는 영역. GC의 대상. Young Generation(Eden+Survivor)과 Old Generation으로 나뉨.
Stack: 스레드마다 별도. 지역 변수, 메서드 호출 정보(프레임) 저장. LIFO 구조.
Method Area: 클래스 메타데이터, static 변수, 상수 풀 저장.
PC Register: 현재 실행 중인 명령어 주소.

GC 과정:
1) 새 객체 → Eden 영역에 생성
2) Eden이 차면 Minor GC → 살아있는 객체는 Survivor로 이동
3) 오래 살아남은 객체 → Old Generation으로 이동 (Promotion)
4) Old가 차면 Major GC (Full GC) → Stop-the-World 발생

증권 시스템 연관: 실시간 주문 처리에서 Full GC로 인한 Stop-the-World는 치명적입니다. 따라서 GC 튜닝(G1GC, ZGC 등)이 중요합니다.
Q17. "synchronized와 ReentrantLock의 차이를 설명해주세요"
synchronized:
- Java 키워드 (메서드/블록 단위)
- 자동으로 Lock 획득/해제
- 공정성(fairness) 설정 불가
- tryLock, timeout 불가

ReentrantLock:
- java.util.concurrent 클래스
- 명시적 lock()/unlock() 호출 (try-finally 필수)
- 공정성 설정 가능 (new ReentrantLock(true))
- tryLock(timeout) 가능 → 데드락 방지
- Condition으로 세밀한 스레드 제어

WhaleArc에서: 사용자별 Lock 분리가 필요하므로 ConcurrentHashMap<String, ReentrantLock>을 사용. synchronized는 객체 단위라 사용자별 분리가 어렵습니다.
Q18. "Spring의 의존성 주입(DI)이란 무엇이고, 왜 사용하나요?"
정의: 객체가 필요한 의존성을 직접 생성하지 않고, 외부(Spring Container)에서 주입받는 것.

WhaleArc 예시:
ExchangeAccountService는 AESCryptoUtil, KisApiClient 등이 필요합니다.
- DI 없이: new AESCryptoUtil(key)를 직접 생성 → 결합도 높음, 테스트 시 Mock 교체 불가
- DI 적용: @RequiredArgsConstructor로 생성자 주입 → Spring이 Bean을 자동 주입

주입 방식:
- 생성자 주입 (권장): 불변성 보장, 순환 의존성 컴파일 타임 감지
- 필드 주입 (@Autowired): 간결하지만 테스트 어려움
- Setter 주입: 선택적 의존성에 사용

장점: 결합도 낮춤, 테스트 용이, 코드 재사용성 향상
Q19. "HTTP와 WebSocket의 차이를 설명해주세요"
HTTP: 요청-응답 모델. 클라이언트가 요청하면 서버가 응답. 단방향. 매 요청마다 연결 수립/해제 (혹은 Keep-Alive).

WebSocket: 양방향 실시간 통신. 한번 연결(Handshake) 후 지속적인 데이터 교환. 서버가 클라이언트에 능동적으로 데이터 전송 가능.

WhaleArc 적용:
- 현재: HTTP Polling (5~10초마다 시세 조회) → 불필요한 요청 다수 발생
- 향후: WebSocket으로 전환 → 시세 변경 시에만 서버가 Push → 트래픽 절감 + 실시간성 향상

증권 시스템: 실시간 시세 피드, 체결 통보에는 WebSocket(또는 FIX/TCP 스트림)이 필수입니다.
Q20. "SQL Injection이란 무엇이고 어떻게 방어하나요?"
정의: 사용자 입력에 SQL 구문을 삽입하여 DB를 비정상적으로 조작하는 공격.
예: ' OR 1=1 --를 로그인 폼에 입력하면 모든 사용자로 로그인 가능.

방어 방법:
1) Prepared Statement (파라미터 바인딩): 가장 기본적이고 효과적. 입력값이 SQL 구문으로 해석되지 않음
2) ORM 사용: Spring Data MongoDB/JPA가 쿼리를 자동 생성 → SQL Injection 원천 차단
3) 입력 검증: 화이트리스트 기반으로 허용된 문자만 통과
4) 최소 권한 원칙: DB 계정에 필요한 최소한의 권한만 부여

TTA 경험: Chakra Max 보안 검사에서 주석/인코딩 변형으로 SQL 차단을 우회한 경험이 있어, 단순 패턴 매칭이 아닌 구조적 방어(Prepared Statement)가 필수라는 것을 체감했습니다.

면접에서 반드시 어필할 차별화 포인트

1. "금융 지식으로 코드 버그를 잡았다"

일목균형표 후행스팬 방향 오류 → 코드상 에러가 아닌 논리적 오류 → 금융 지식이 없으면 발견 불가능. 미래에셋에서도 "현업의 요구사항을 수동적으로 구현하는 것이 아니라, 비즈니스 결함을 선제적으로 발견"할 수 있습니다.

2. "실제 증권 시스템과 같은 성격의 문제를 경험했다"

동시 주문 잔고 정합성 문제 → Lock으로 해결. 규모는 다르지만 본질은 동일합니다. 실제 OMS에서 DB Lock, 분산 Lock으로 확장하는 방법도 이해하고 있습니다.

3. "보안을 설계 단계에서 고려한다"

TTA에서 "뚫는 경험" → WhaleArc에서 "막는 설계". JWT 6중 보안 (XSS/CSRF/Replay/로그아웃/스푸핑/에러노출 방어), AES-GCM 암호화, API 키 마스킹까지 적용.
